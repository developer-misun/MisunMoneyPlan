# 의사결정 기록 (Decision Log)

이 문서는 기술적 선택이나 디자인 결정의 이유(Why)를 기록하여 프로젝트의 일관성을 유지합니다.

## 2026-05-11
### 1. 차트 라이브러리 미사용 및 Canvas 직접 구현
- **결정**: 외부 차트 라이브러리 대신 Jetpack Compose `Canvas`로 직접 구현.
- **이유**: 커스터마이징 자유도를 높이고, 트리맵 알고리즘(Slice-and-Dice)을 프로젝트 요구사항에 맞게 최적화하기 위함.

### 2. '종목별' 트리맵 vs '유형별' 파이차트 분리
- **결정**: 데이터 관점에 따라 차트 종류를 다르게 적용.
- **이유**: 
    - **종목별**: 개별 자산의 비중을 면적으로 직관적으로 비교하기 위해 트리맵이 유리. (상위 10개 제한 없이 시각화)
    - **유형별**: 전체 포트폴리오의 자산군 비율을 전통적인 도넛 차트로 보여주는 것이 사용자에게 익숙함.

### 3. 패키지 구조: 컴포넌트 전역화 (`presentation.components`)
- **결정**: `home.components`에서 `presentation.components`로 이동.
- **이유**: 차트나 자산 리스트 UI가 상세 화면이나 요약 화면 등에서 재사용될 가능성이 높음.

## 2026-05-13
### 1. 하드코딩된 문자열 리소스화 관리
- **결정**: 모든 UI 내 하드코딩된 문자열을 `strings.xml`로 추출하여 관리.
- **이유**: 유지보수 편의성, 일관된 문구 관리, 그리고 향후 다국어 지원을 위한 기초 마련.
- **규칙**: 신규 문자열 추가 시 반드시 `strings.xml`을 거쳐서 참조하도록 함.

### 2. 타입 안전한 네비게이션 구조 도입
- **결정**: 문자열 리터럴 기반의 Route 관리 대신 `Sealed Class`를 활용한 타입 안전한 네비게이션 구조 채택.
- **이유**:
    - Route 명칭 오타로 인한 런타임 에러 방지.
    - 화면별 필요한 인자(Arguments)를 명확히 정의하여 데이터 전달의 안전성 확보.
    - 네비게이션 로직의 중앙 집중화로 유지보수성 향상.
- **구현 방식**: `presentation/navigation/Screen.kt`를 정의하여 각 화면의 Route와 인자 생성 로직을 캡슐화함.

## 2026-05-13
### 1. UiState 고도화 및 에러 핸들링 체계 구축
- **결정**: `UiState`에 로딩(`isLoading`) 및 에러 메시지(`errorMessage`) 상태를 추가하고, UI에서 이를 처리하도록 구현.
- **상세 처리 방식**:
    - **로딩 상태**: 데이터 로드 중에는 화면 중앙에 `CircularProgressIndicator`를 노출하여 사용자에게 진행 상황을 알림.
    - **에러 상태**: 데이터 로드 실패 시 에러 메시지와 함께 '재시도(Retry)' 버튼이 포함된 뷰를 노출함.
    - **상태 전이**: `loadAssets()` 호출 시 `isLoading = true` -> 성공 시 `isLoading = false, assets = data` -> 실패 시 `isLoading = false, errorMessage = message`.
- **이유**: 사용자에게 데이터 로드 상태를 명확히 알리고, 예외 상황 발생 시 일관된 피드백을 제공하기 위함.

### 2. 도메인 레이어 UseCase 분리 (향후 과제)
- **개념**: ViewModel에 집중된 비즈니스 로직(예: 그룹화, 계산)을 독립적인 `UseCase` 단위로 분리.
- **이유**: 코드 재사용성을 높이고 비즈니스 로직만 별도로 단위 테스트하기 위함.

### 3. DI 모듈을 통한 인터페이스 주입 강화 (향후 과제)
- **개념**: Repository 인터페이스와 구현체를 Hilt 모듈로 명확히 바인딩하여 관리.
- **이유**: 실제 DB 연동이나 테스트용 가짜 데이터로의 교체가 유연해지도록 결합도를 낮춤.
